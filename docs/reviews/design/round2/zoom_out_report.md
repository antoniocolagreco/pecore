# PeCore Initial Zoom Out Review

The two reviewers evaluated the full design in separate contexts. Both read the UI specification, concepts brief, initial brainstorm, prior ACP review, and the ACP, macOS Keychain, and Linux harness spike reports. The specification spans lines 1–853 and the implementation plan spans lines 854–1274. [Design](docs/design.md) · [UI specification](docs/ui-design.md)

## Blockers

1. **An interrupted rebase can roll back another job’s stash.** Jobs share `repo.git` and its `refs/stash`. The shipped rebase uses the latest stash, and interruption recovery resets the shared ref to its previous value. Give rebase and rollback checkpoints a job owner. Verify that interrupting one of two concurrent rebases preserves both jobs’ changes. PeCore will need to remove abandoned checkpoints. Both reviewers found this. [Rollback](docs/design.md#L540) · [Shared repository](docs/design.md#L545) · [Rebase template](docs/design.md#L1232)
2. **Delivery probes can misclassify incomplete or unknown effects.** The push probe treats a remote lookup failure like an absent commit. The repo creation probe checks that the repo exists, so a crash before the initial push can leave an incomplete project marked ready. Preserve `unknown` when a lookup fails. Make repo creation and initial branch publication independently verifiable and resumable within the template. Verify recovery between those steps. Both reviewers found this. [Recovery rule](docs/design.md#L569) · [Shipped probes](docs/design.md#L1233) · [Repo creation](docs/design.md#L243)

## Major findings

3. **Checks and human approval can refer to different content.** Before and after hashes of a writable workdir cannot show what a check read during its run. The shipped commit gate requires lint, typecheck and tests, and a human approval can survive a content change without the same check. Run required checks against a pinned snapshot and bind required check and approval records to the snapshot or an explicitly approved patch. Include the relevant node definition so the recipe can decide whether edits invalidate earlier evidence. Snapshots cost disk and setup time. Inventive Catalyst finding. [Commit gate](docs/design.md#L356) · [Content state](docs/design.md#L530) · [Live node edits](docs/ui-design.md#L300)
4. **A crash can leave a ticket recorded as seen without a job.** The intake design records seen IDs and then hands tickets to the orchestrator. Persist a pending intake record in the existing project database and give job creation a stable intake ID. On restart, resume pending tickets and reuse any jobs already created for that ID. Orders split into several jobs need a defined replay rule. Inventive Catalyst finding. [Source intake](docs/design.md#L720) · [Ticket data model](docs/design.md#L907)
5. **The engine owns forge-specific choices despite the templates-only extension goal.** Clone and fetch use forge-specific credential helpers, and the engine chooses starter nodes by forge. Keep clone and fetch generic and define account setup and starter node selection alongside the forge templates. Zoom Out finding. [Forge goal](docs/design.md#L66) · [Clone and fetch](docs/design.md#L244) · [Project creation](docs/design.md#L990) · [Credential handling](docs/design.md#L1129)
6. **The approval check and command execution need the same inputs.** The plan hashes the approved snapshot, then checks the files before use. Specify that the runner executes the very definition and script bytes it checked, including probes. Otherwise a file edit between the check and execution can bypass the approval guarantee. Zoom Out finding. [Approval rule](docs/design.md#L739) · [Confirmation implementation](docs/design.md#L1098) · [Command and probe runners](docs/design.md#L1125)
7. **Waiting for a forge can tie up job slots.** The release rule names human, quota, login and confirmation waits. A network probe can wait indefinitely, so a forge outage can leave jobs holding slots that other projects need. Release execution slots whenever no attempt is active and reacquire them before the next attempt. Keep any running services under their existing lifecycle rules. Zoom Out finding. [Wait reasons](docs/design.md#L526) · [Network probe](docs/design.md#L572) · [Pool implementation](docs/design.md#L1111)
8. **The phase 3 acceptance job cannot run as specified.** The shipped `feature` recipe requires a reviewer from another provider and ends with an open PR. Phase 3 has one connector and a local project. Use an explicit local single-provider recipe for that gate and preserve the release gate with three providers. First run accepts one model account, so show which accounts and delivery targets each offered recipe needs. The local recipe needs its own acceptance case. Both reviewers found this. [Feature recipe](docs/design.md#L336) · [Local-only recipe](docs/design.md#L1245) · [Phase 3](docs/design.md#L1271) · [First run](docs/ui-design.md#L320)
9. **The bugfix recipe never proves the test reproduces the bug before the fix.** The recipe asks for a failing test, then typechecks before the builder runs. Use the existing command runner to verify that the regression test fails for the reported reason on the original code and passes after the fix. Zoom Out finding. [Before-build check](docs/design.md#L348) · [Bugfix template](docs/design.md#L1244)
10. **First run blocks local normal-mode work on tools for optional features.** The setup checks require `sudo`, Linux `setfacl`, Compose and gitleaks. Check them before the user enables protected mode, starts job services or exports history, respectively. Zoom Out finding. [Prerequisite checks](docs/design.md#L1090) · [First-run steps](docs/ui-design.md#L324)

## Minor findings

11. **Implementation instructions interrupt the architecture.** Move full shell examples, vendor payload keys and file operations to the implementation plan or connector fixtures. Keep the inputs, outputs and guarantees in the architecture. Zoom Out finding. [Command example](docs/design.md#L296) · [Provider data](docs/design.md#L647) · [File access](docs/design.md#L732)
12. **The repository inventory omits existing ACP fixtures.** The implementation plan says the repo holds only `docs/`, but `packages/agents/fixtures/` already contains recorded sessions. The spike client also provides a starting point for ACP framing and request dispatch. Point the implementation plan to these assets. The code search found no production implementation to reuse. Zoom Out finding. [Inventory](docs/design.md#L856) · [Existing fixtures](packages/agents/fixtures/) · [ACP spike client](docs/spikes/acp/client.mjs)
