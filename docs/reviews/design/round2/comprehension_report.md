## What this proposes

PeCore is a local desktop app that turns chat orders and tracker tickets into software jobs. An orchestrator chooses the work and creates jobs, then a TypeScript engine follows each job’s recipe through agent, check, human review and delivery nodes. Jobs run in separate Git worktrees, can depend on earlier jobs, and bind checks and delivery to specific file content. Agent connectors use the user’s installed harnesses through ACP, while PeCore records job state in SQLite and uses probes to recover when an external action may already have happened.

## How the existing system works, per this document

The document describes a repository containing design work and spikes, with the factory itself still to be built. The spikes recorded ACP behavior for Claude Code, Codex and opencode and investigated login storage on Linux and macOS. The proposed protected-mode run through `sudo`, including process cleanup and repository MCP behavior, remains an open check.

## Findings

- **Blocker · Phase 3 acceptance gate.** I cannot explain how to run the specified gate using the definitions given. Phase 3 calls for a `feature` job on a local-only project. That project receives only `local-only`, while `feature` requires a push and a GitHub PR. The gate needs to name a local adaptation of `feature` or identify the recipe that actually runs. [Feature recipe](docs/design.md#L336) · [Recipe selection](docs/design.md#L1093) · [Phase 3](docs/design.md#L1271)
- **Major · Local project creation.** `repo: null` is valid, and the creation sequence branches only on whether a remote exists. The reader has to infer how a local-only project gets its initial base branch and whether it bypasses `createRepo`, account validation, and the fetch performed at job creation. The CLI section also cites admin setup and logins as reasons creation is GUI-only, while the creation sequence says those steps are unnecessary for a new project. [Project fields](docs/design.md#L464) · [Creation sequence](docs/design.md#L988) · [Job creation](docs/design.md#L999) · [CLI](docs/design.md#L1215)
- **Major · Confirmation during remote creation.** Project creation promises rollback on a failed step, and `createRepo` can wait for confirmation or a probe before completing. The wizard lists Create and Confirm as distinct pages. The reader cannot tell when the user can confirm the pseudo-job, what state persists while it waits, or what happens if the remote is created and a later local step fails. [Confirmation rule](docs/design.md#L739) · [Creation sequence](docs/design.md#L988) · [Wizard](docs/design.md#L1201)
- **Major · Stacked job base and realign.** Job creation sets a base commit and target even though a queued child cannot yet know its parent’s final commit. Worktree creation uses the parent’s last commit. The document leaves open when the stored base, old base and target acquire their real values. It also says the orchestrator can request realignment, yet its tool list has no tool for that action. [Base change](docs/design.md#L512) · [Stacked jobs](docs/design.md#L550) · [Orchestrator tools](docs/design.md#L706) · [Job creation](docs/design.md#L999)
- **Major · Probe completion and push.** `done` is a probe result, while the graph advances on node outcomes such as `opened` or `pushed`. The document does not specify how the executor picks the node outcome when the command is skipped. For push, the command also needs the remote SHA from the probe when the remote differs from the desired commit. The listed probe prints a SHA only when they match and treats a failed lookup like an empty result. [Probe rules](docs/design.md#L278) · [Probe execution](docs/design.md#L572) · [Push command](docs/design.md#L873) · [Push probe](docs/design.md#L1233)
- **Major · Ticket intake without a tracker source.** A project may have no source, and the GitHub issue journey never says to configure one. The only defined ticket reader belongs to a source. The document also gives a tracker-user trust rule without explaining what authorship or label information `markdown-folder` can return. [GitHub issue journey](docs/design.md#L119) · [Project source](docs/design.md#L470) · [Sources](docs/design.md#L715) · [Markdown source template](docs/design.md#L1240)
- **Major · Agent questions.** The database, chat UI and `answer_question` tool all assume that an `agent-question` item exists. Neither an agent’s output protocol nor the orchestrator’s tools describe how to create one. A reader cannot follow a question from the agent to the user, see whether the job waits, or determine how the answer reaches the next turn. [Wait states](docs/design.md#L514) · [Orchestrator tools](docs/design.md#L706) · [Queue data](docs/design.md#L916) · [Answer handler](docs/design.md#L1161) · [Chat UI](docs/design.md#L1197)
- **Major · Protected-mode switch and user control.** Protected mode is presented as one setting that switches all projects to a shared OS user. Project deletion can offer to remove that user, and project import names an OS-user choice. The document leaves open whether a project can choose a different user, and whether an active node can continue under its old user when protected mode is enabled. [Global mode decision](docs/design.md#L18) · [Project deletion](docs/design.md#L574) · [Mode switch](docs/design.md#L865) · [Project import](docs/design.md#L1168)
- **Major · Quit and job services.** The service lifecycle assigns shutdown cleanup to the Electron main process in one section and to the engine in another. On normal quit, cleanup removes the containers and their data. The restart path offers to play interrupted jobs, and the general play rule says to start existing containers. The reader cannot tell whether those interrupted jobs get fresh services or try to restart removed ones. [Job services](docs/design.md#L578) · [Quit sequence](docs/design.md#L984) · [Engine shutdown](docs/design.md#L1085)
- **Major · Archive and resume.** A failed or stopped job can be resumed in the same workdir. The user can also archive either state, and archiving removes its workdir. The document leaves open whether an archived job can resume, and what code or artifacts it resumes from if its workdir is gone. [Job controls](docs/design.md#L84) · [Job states](docs/design.md#L483) · [Workdir cleanup](docs/design.md#L548)
- **Nit · `MCP` and `identityField`.** The text explains what the orchestrator’s MCP server does and leaves the acronym unexpanded. `identityField` is named alongside `identityCommand`. Its result format and what value it selects are unspecified. [Login configuration](docs/design.md#L437) · [Orchestrator server](docs/design.md#L705) · [Connector schema](docs/design.md#L943)
