# PeCore Intermediate Zoom Out Review

Stage 8 covers the full design, including the specification and implementation plan. The reviewer read the seven selected context files and compared the Stage 5, 6 and 7 reports. The design and UI specification match their Git versions. The findings below describe open gaps and the conditions each proposed fix would need to meet. [Design](docs/design.md) · [Stage 5](zoom_out_report.md) · [Stage 6](comprehension_report.md) · [Stage 7](critic_report.md)

## Blockers

- **Bind approval, checks and delivery to the same tree.** Stage 7 elevated the Stage 5 evidence concern. A pinned input helps only if it stays stable while the check runs. Record the tree shown to the reviewer, the applicable node definition and the result. Check the approval and required checks at the commit gate. If a recipe allows approval to carry over after a rebase, define what approval of an unchanged patch covers and rerun checks on the new tree. For command confirmations, execute the same definition and script bytes the runner verified. [Recipe gates](docs/design.md#L376) · [Content state](docs/design.md#L530) · [Confirmation runner](docs/design.md#L1098) · [Live edits](docs/ui-design.md#L300)
- **Give rollback state a job owner.** Stages 5 and 7 found that a rebase can consume another job’s stash and its recovery can reset the shared ref. Keep the shared repository and make rebase, restore and cleanup use job-owned checkpoints. The planned tests cover one interrupted rebase. Verify that interrupting either of two concurrent rebases preserves both jobs’ changes. Use attempt-owned storage for agent output so a retry cannot reuse a stale result. [Rollback](docs/design.md#L540) · [Agent output](docs/design.md#L691) · [Recovery tests](docs/design.md#L1008) · [Rebase template](docs/design.md#L1232)
- **Use one recovery contract for external actions.** Stage 6 showed what `unknown` alone leaves open. A completed probe must supply the graph outcome, and a push that still needs to run needs the observed remote head. Stage 7 added the need to distinguish authentication failures from network failures for both probes and commands. Keep these rules in the command runner and forge-specific observations in the templates. The UI already places repo creation approval inside Create and reports a remote left after local undo. The implementation needs a setup record that survives a wait or restart and can verify both repo creation and initial branch publication. [Probe contract](docs/design.md#L278) · [Crash recovery](docs/design.md#L569) · [Project creation](docs/design.md#L986) · [Push probe](docs/design.md#L1233) · [Wizard](docs/ui-design.md#L260)
- **Define which service configuration PeCore can run.** Stage 7 found that reading Compose configuration from the base commit and asking for confirmation leave the allowed configuration undefined. Define the supported service fields and validate the resolved configuration. Confirm the exact input the runtime receives. Stage 6 also found two owners for shutdown cleanup. Give the engine one service lifecycle and specify how Play recreates services after Quit removes them. [Job services](docs/design.md#L576) · [Quit](docs/design.md#L984) · [Service implementation](docs/design.md#L1146)
- **Make the Phase 3 gate runnable using one connector and a local repo.** Stage 6 showed why changing the recipe name alone is insufficient. The local setup still needs a rule for initializing the base branch and skipping forge account validation and fetch. Name a local single-provider recipe and verify the path from project creation to a commit. Keep the Phase 6 three-connector gate. The same local path can check that only prerequisites for selected features block onboarding. [Project creation](docs/design.md#L986) · [Starter recipes](docs/design.md#L1092) · [Build gates](docs/design.md#L1266) · [First run](docs/ui-design.md#L320)

## Major findings

- **Track delivery independently of the final recipe outcome.** Stage 7 found that a stacked child needs its parent’s actual merge target. The merge watcher also follows only `succeeded` parents. The `bugfix` recipe can leave a PR open and end in failure if the ticket comment fails. Drive merge detection from the recorded PR or MR and its target. Define when a queued child receives its base and retain parent refs while a child needs them. [Stacked jobs](docs/design.md#L550) · [Job creation](docs/design.md#L997) · [Merge watcher](docs/design.md#L1138) · [Bugfix recipe](docs/design.md#L1244)
- **Persist ticket intake through job creation.** Stages 5 and 7 identified the gap between recording a ticket as seen and giving it to the orchestrator. Store pending intake in the project database and use a stable request ID. For an order split into jobs, record the job plan or stable child IDs so a retry can reuse work already created. Define when to acknowledge the ticket and how chat ticket references work with polling off or with no source. For the storage choice, say which state the engine rebuilds from events, or describe those events as history. SQLite transactions alone can support either design. [Project storage](docs/design.md#L242) · [Sources](docs/design.md#L713) · [Storage alternative](docs/design.md#L796) · [Intake implementation](docs/design.md#L1163)
- **Carry the OS boundary through the UI, plan and acceptance checks.** The UI defines one global mode switch and maps accounts on import. Align the plan and specify what happens to running jobs during a switch. In normal mode, agents share the app user and that user’s access to the local API and database. In protected mode, the shared agent user can access protected harness logins. The proposed `sudo` spike covers process and connector behavior. Add a packaged protected-mode check that verifies orchestration after restart with the new MCP token and the intended tool set. The spike checked the Claude account connector setting with `claude -p`. The ACP check remains open. [Local API](docs/design.md#L202) · [Orchestrator](docs/design.md#L702) · [Protected mode](docs/design.md#L725) · [Phase 0 check](docs/design.md#L1013) · [Spike evidence](docs/spikes/acp.md#L63)
